# Client Windows build entry

Run `Build-Client.ps1` in a Windows MSVC environment with CMake, Cargo, the x86_64-pc-windows-msvc, i686-pc-windows-msvc and aarch64-pc-windows-msvc Rust targets, the Visual Studio ARM64 and ARM64EC build tools (`Microsoft.VisualStudio.Component.VC.Tools.ARM64` and `...ARM64EC`), and clang on PATH: ring, which the host links, assembles its ARM64 code with clang only. Visual Studio's own clang (`Microsoft.VisualStudio.Component.VC.Llvm.Clang`, `VC\Tools\Llvm\x64\bin`) will do. Supply separate absolute native dependency prefixes for x64 and x86 with the packages listed in `vcpkg.json` (`curl`, `fmt`, `nlohmann-json`, `utfcpp`):

```powershell
# 与 vcpkg.json 的 builtin-baseline 一致的 vcpkg checkout
git clone https://github.com/microsoft/vcpkg.git C:\vcpkg
git -C C:\vcpkg checkout ef7dbf94b9198bc58f45951adcf1f041fcbc5ea0
C:\vcpkg\bootstrap-vcpkg.bat -disableMetrics
C:\vcpkg\vcpkg.exe install --triplet x64-windows --x-manifest-root=platforms/windows --x-install-root=C:\deps\x64
C:\vcpkg\vcpkg.exe install --triplet x86-windows --x-manifest-root=platforms/windows --x-install-root=C:\deps\x86

.\platforms\windows\Build-Client.ps1 -X64Dependencies C:\deps\x64\x64-windows -X86Dependencies C:\deps\x86\x86-windows
```

The Rust half of the client (the x64, x86 and ARM64 host DLLs) does not depend on the edition, so it is built by `Build-RustOutputs.ps1 -Architecture x64|x86|arm64 -OutputDirectory <dir>`, which collects each architecture's outputs under fixed names in `<dir>/<arch>`. `Build-Client.ps1 -RustOutputs <dir>` takes them from there and runs no cargo command; this is how `release-windows.yml` builds the Rust half once, one job per architecture in parallel, for every edition. Without `-RustOutputs`, `Build-Client.ps1` runs `Build-RustOutputs.ps1` itself for all three architectures into `target/windows-rust`, so a local build needs the Rust toolchain and clang listed above.

未签名构建默认显式设置 `MSIME_SERVER_UIACCESS=OFF`，可在普通应用中启动 Server。只有随后用受信任证书签名并安装到安全目录的包才传 `-ServerUiAccess`；`Package-SimplySign.ps1` 和本地签名安装入口会传入，发布工作流只在生产 SignPath 签名时传入。nightly、未签名包和 SignPath 测试证书包均不启用；普通权限包不具备可信 UIAccess 包跨完整性级别的能力。

The default CMake generator is Visual Studio 2022. Each prefix must contain libraries built for its architecture and a compatible MSVC runtime; this script does not download or build dependencies, alter Rust toolchains, sign binaries, register TSF, invoke CI, or install the input method.

The x64 build includes Server, Watchdog, preparation tool, native WinUI 3 settings and TSF. The x86 build contains the in-process TSF and matching Host DLL, not another Server. The arm64 build contains the TSF DLL for Windows on Arm, which is [Arm64X](https://learn.microsoft.com/windows/arm/arm64x-build): native ARM64 processes (Explorer, Edge, Notepad) and emulated x64 processes load it through the same registration, so it carries ARM64 code for the first and ARM64EC code for the second. `tsf/CMakeLists.txt` links it in two passes (`MSIME_TSF_ARM64X=ARM64`, then `ARM64EC`, sharing the linker response file the first one writes). The ARM64 half imports an ARM64 host DLL built here with a static C runtime and named after the edition's host DLL with `_arm64` appended (`msime_host_api_arm64.dll`); the ARM64EC half imports the x64 host DLL, which runs emulated. Everything else stays x64 and runs emulated on Windows on Arm. Native outputs go to `target/windows-full/<arch>/bin`. Rust release artifacts remain under the explicit target triple, with debug information enabled; native CMake uses RelWithDebInfo. The WinUI 3 project is built self-contained and staged as `msime-client-settings.exe`; both it and the Server keep their PDB beside the executable, and a missing settings output fails the build. `Prepare-PackageFiles.ps1` prefers the staged WinUI settings binary when no `DesktopExecutable` override is supplied.

Every native command exit status is checked immediately. The caller's directory and dependency prefix, and in `Build-RustOutputs.ps1` the Cargo target directory, release-debug setting, ARM64 Rust flags and `MSIME_VERSION`, are restored on success or failure. `tests/tools/build_client.ps1` tests the orchestration using command probes, including failure at every stage; it drives probes rather than a compiler, so it covers the ordering and the error handling, not the native build itself or its runtime dependency closure.

Before reporting completion, the build reads PE headers from all four x64 EXE outputs (`MetasequoiaImeServer.exe`, `MetasequoiaImeWatchdog.exe`, `msime-client-prepare.exe`, `msime-client-settings.exe`), the TSF/Host DLL pair for x64 and x86, and the Arm64X TSF DLL with its ARM64 host DLL; for the Arm64X DLL it also requires the hybrid metadata that only an Arm64X image carries, so a plain ARM64 build cannot pass. It rejects missing or truncated headers, wrong machine or optional-header type, and EXE/DLL flag mismatches. `Test-PortableExecutable.ps1` can also inspect individual outputs without loading them. Header fields follow Microsoft's [PE format specification](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format). This is an architecture/type gate, not full image validation, signature checking, import resolution or Windows runtime verification. Parser fixtures intentionally contain only synthetic headers; they are not executable images.

The build also collects top-level release `bin/*.dll` from each explicitly provided dependency prefix. Every candidate passes the PE architecture/DLL gate before copying; same-named different output content causes failure rather than overwrite. Identical files are reused. Static prefixes may have no bin directory. Debug subdirectories and non-DLL files are not copied. Each TSF staging directory carries these ordinary dependencies without COM registration; the Server package already copies its output directory recursively.

This collects all release DLLs from the supplied prefixes, not only imported ones. It is not recursive import analysis: Windows components, VC runtime redistribution and dynamically loaded modules outside those prefixes still need explicit provisioning and verification. Distribution must retain the licenses for supplied dependency packages; prefix collection is not a license audit.

`installer/test.ps1` and `test-light.ps1` call this entry through the shared local install workflow. They require both dependency prefixes and an explicit notice directory, then stage, self-sign, compile and launch the installer. Use this build-only entry when those local-machine side effects are not intended. See `installer/LocalInstall.md` for scope and verification limits, and `installer/README.md` for the unsigned and signed packaging steps.
